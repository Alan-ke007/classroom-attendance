# 智课考勤系统 — 功能分析（场景驱动 v0.2）

> 分析方法：不从"9 大模块清单"出发，而是还原**三类角色在校园里的真实一天**，从场景里倒推"到底需要什么功能"，再回过头对照现有 9 模块——哪些覆盖了、哪些缺了、哪些其实在真实场景里是冗余的。
>
> 结论先行：9 大模块**方向基本对**，但有一半是"锦上添花"，真正撑起产品价值的只有 4 个闭环功能；同时有 **7 个真实刚需当前是缺口**（最致命的是"防代签"和"课表对接教务"）。

---

## 1. 三类角色的真实场景还原

### 场景 A · 学生的一天（手机为主）
- **8:00 早八《高等数学》**：老师课前 5 分钟发起签到，张三掏手机扫小程序码 → 签到成功。
- **8:05 张三才扫**：系统应标记"迟到"，而不是"正常"——需要**签到时间窗 + 迟到阈值**。
- **张三没来**：整节课没扫 → 缺勤；但如果他其实请了病假（传了病历），系统应自动归为"请假"而非"缺勤"。
- **代签现实痛点**：张三把二维码截图发寝室群，李四帮扫 → 系统记张三"已到"但实际人不在。**这是高校考勤的头号难题，纯二维码解决不了。**
- **误判**：张三手机没电、扫码失败，被记缺勤 → 他需要能**申诉**，老师能手动补签。

### 场景 B · 教师的一天（桌面 Web 为主）
- 课前发起签到（二维码 / 位置 / 人脸，按教室条件选）。
- 课中看实时看板：谁到了、谁迟到、谁没到。
- 课中 YOLOv8 推预警："第 3 排右睡"——教师能即时干预。
- 批请假：张三请病假，附病历图，教师批/驳，审批意见留痕。
- 下课导出考勤 Excel 交教务；**但课程表是手动建的，和真实教务系统对不上就全错**。
- **调课/补课/节假日**：真实校园高频发生，当前系统无此概念。

### 场景 C · 辅导员 / 管理员（桌面 Web + 大屏）
- 辅导员（**当前系统缺这个独立角色**）要巡课看整体出勤、接**缺勤自动预警**（"张三连续 3 次缺勤"），拿数据找学生谈话。
- 管理员做用户/班级/课程/系统配置、看全局统计与数字孪生大屏。

### 场景 D · 算法侧（技术 Reality）
- 教室摄像头推流 → YOLOv8 推理（举手/写字/睡觉/玩手机）→ 入库 + WebSocket 推预警。
- **现实约束**：多教室并发性能、学生被监控的**隐私合规与告知**、弱网/离线容错。

## 2. 从场景倒推：真正需要的功能（按闭环切片）

| 闭环 | 场景驱动出的功能 | 当前 9 模块覆盖？ |
|------|----------------|------------------|
| **① 签到闭环** | 多方式签到（二维码/位置/GPS/蓝牙信标/**人脸防代签**）、签到时间窗与迟到/早退判定、手动补签、弱网缓存后同步 | 部分（仅二维码 + 3 态，缺人脸/迟到早退细分/弱网） |
| **② 课程班级闭环** | 班级/学生/课程 CRUD、**课表导入对接教务系统**、调课/补课/节假日日历 | 部分（缺对接 + 调补课） |
| **③ 请假闭环** | 学生提交（事/病 + **病历附件**）、教师审批留痕、请假自动关联考勤状态、**误判申诉** | 基本覆盖（附件/申诉偏弱） |
| **④ 行为监控闭环** | YOLOv8 实时检测、WebSocket 预警推送、行为统计、**隐私合规告知** | 覆盖（合规待补） |
| **⑤ 预警与统计闭环** | 缺勤自动预警规则（连续 N 次推辅导员）、出勤率/迟到率趋势、班级排名、**导出对接教务** | 部分（缺预警规则 + 辅导员角色） |
| **⑥ 通知闭环** | 考勤/行为/请假/系统 四类通知、未读管理 | 覆盖 ✓ |
| **⑦ 沟通闭环** | 师生即时聊天 | 覆盖，但**真实场景被微信/QQ 群替代**（见 §4） |
| **⑧ 展示闭环** | 全局看板 + 校园数字孪生大屏 | 覆盖，但**属 showpiece，非日常刚需** |

## 3. 对照现有 9 模块：覆盖 / 缺口 / 冗余

### ✅ 覆盖到位（保留）
- 用户认证（JWT + 三角色）
- 考勤记录与统计（出勤率/迟到率图表）
- 请假管理（申请→审批→关联考勤）
- 行为监测（YOLOv8 + 预警）
- 消息通知（四类 + 未读）
- 系统管理 / 数据导入（Excel）

### 🔴 真实刚需缺口（当前没有或太弱）—— 重做必须补
1. **防代签 / 人脸核验**：把 YOLOv8 人脸比对接入签到，解决头号痛点；这是 AI 卖点该落地的闭环。
2. **考勤状态细分**：迟到 / 早退 / 请假 / 公假 / 旷课，而非只有"正常/迟到/缺勤"三态。
3. **课表对接教务系统**：真实高校都有教务系统（正方/URP 等），导入课表是刚需，手动建极易错。
4. **调课 / 补课 / 节假日日历**：校园高频，当前无概念。
5. **辅导员独立角色 + 预警分级**：当前只有 admin/teacher/student，辅导员视角缺失。
6. **签到异常申诉**：学生被误判可发起申诉，教师复核。
7. **缺勤自动预警规则引擎**：连续 N 次 / 单课缺勤达阈值 → 自动推辅导员。

### 🟡 存疑 / 冗余（真实场景里 ROI 低，建议降级或砍）
- **即时通讯（聊天模块）**：中国校园师生沟通 90% 在微信群/QQ 群，自建聊天维护成本高、使用率低 → 建议**砍**，或仅做"留言板"级轻量沟通。
- **文件管理（独立模块）**：通用网盘能力，非考勤核心 → 降级为"请假附件 / 资料上传"的轻量组件，不必独立文件模块。
- **数字孪生大屏**：展示 wow 效果好，但非日常操作刚需 → 可后移至二期，作为汇报/迎检用。
- **公告模块**：通知模块已覆盖推送能力，独立公告易冗余。
- **家长通知**：大学生是成年人，**不需要**家长通知（K12 才需要）——明确列为非目标。

## 4. 功能优先级（MoSCoW，基于真实场景必要性）

| 层级 | 功能 | 理由 |
|------|------|------|
| **Must（核心价值，不做不成产品）** | 多方式签到（含人脸防代签）、课程/班级/学生、请假（含附件+审批）、YOLOv8 行为检测、统计看板、三角色权限、消息通知 | 场景 A/B/C/D 天天用 |
| **Should（体验完整，首版尽量有）** | 课表对接教务、调补课/节假日、辅导员角色+预警分级、申诉、迟到/早退细分、预警规则引擎 | 真实校园高频，缺了老师会抱怨 |
| **Could（锦上添花，二期再做）** | 聊天（或轻量留言）、独立文件管理、数字孪生大屏、公告 | 被微信/网盘替代或仅展示用 |
| **Won't（首版不做）** | 家长通知、教务系统双向写回、复杂排课算法 | 成人用户/超出范围/过度工程 |

## 6. 结论与给重做的建议

1. **核心价值闭环只有 4 个**：签到（防代签）→ 请假关联 → 行为监控 → 统计预警。重做资源优先砸这里。
2. **9 模块"全保留"不等于"全平级"**：按 MoSCoW 分层，聊天/文件/大屏降为 Could，避免首版背上全量重负（与你之前定的"保留 9 模块"不冲突——保留但分层）。
3. **两个最该补的缺口**：① 人脸防代签（AI 卖点真正落地）；② 课表对接教务（否则课程班级数据全是错的）。这两项是"做了就质的飞跃，不做就只是又一个考勤 Demo"。
4. **补一个被忽略的角色**：辅导员。高校考勤的"消费者"往往是辅导员而非任课老师，缺这个角色产品不完整。
5. **面试视角**：这份分析的价值在于——你不是"按清单堆功能"，而是"从真实场景倒推功能、并能果断砍掉 ROI 低的模块"。这比罗列 9 个模块更有产品感，面试官更买账。
